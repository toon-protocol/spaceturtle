# Developing spaceturtle

[`CLAUDE.md`](../CLAUDE.md) describes how the repository is worked on, including by the AFK factory.

## Tests

`tests/run` runs the answers the `being-observed` skill describes against Request files, and the launcher's `spaceturtle start`, `stop`, `upgrade`, `backup`, `remove`, `waiting`, `approve`, `refuse`, `ask`, `persona`, `requests`, `withdraw`, `status` and `agent-key`, `session`, and `install.sh`, against a stub `msb`, in a temporary home, holds the agent definition to the safety rules of ADR 0003 through `tests/check-agent`, holds the zone images' files to their pins through `tests/check-images`, and runs the `release/` scripts against a stub `docker-agent`. The panel's tests are in [its repository](https://github.com/toon-protocol/spaceturtle-panel). It needs bash, `jq` and `yq` (mikefarah's), and is what the `gate` job of `.github/workflows/ci.yml` runs.

## Files

| File | |
| --- | --- |
| `skills/being-observed/SKILL.md` | The agent's skill: the public key file, the Persona (creating, reading and living by it, renaming the relay), reading the Requests, answering them, writing a Renderer for a kind |
| `spaceturtle` | The launcher: `spaceturtle start` brings up the connector's zone on devnet from the connector's zone image (`SPACETURTLE_CONNECTOR_IMAGE`), copying nothing in from the machine, doing only the steps not yet done, with its step markers in `~/.local/state/spaceturtle/launcher`; `start`'s flags choose the network (`--network`, `--evm-rpc-url`, `--evm-chain-id` and the rest of `toon init`'s), kept in `launcher.conf`; `session`, `timer`, `set` and `key` start the agent's sessions, by hand and on a timer, and keep its settings in `~/.config/spaceturtle/launcher.conf`; `waiting`, `approve` and `refuse` list, approve and refuse the apps the agent node holds until the Observer approves them; `ask`, `persona`, `requests` and `withdraw` write, list and withdraw Requests in the queue the agent's zone mounts, and an unattended session leaves a report in `last-session` and sends a desktop notification; `start` also makes the agent key once, and `agent-key show`, `replace`, `revoke` and `limit` show, replace, revoke and limit it from outside the agent's zone; `status` shows the timer and the last unattended session, each zone's state, the node's network, its apps and relay, whether the supervisor runs and how many apps wait; `stop`, `upgrade`, `backup` and `remove` stop, replace, back up and remove the Install (`upgrade` carries the passphrase in memory through `msb exec`; `remove` keeps the wallet's storage and the backup directory); `supervise` is what the unit that keeps the connector's zone running runs |
| `install.sh` | The one command a person runs first: checks the machine, installs the launcher and the agent definition of a release with a `version` file beside them (the launcher then pulls that release's zone images), links it into `~/.local/bin`, and puts the pinned microsandbox (`msb`), which the zones run in, in `~/.local/share/spaceturtle/msb` |
| `agent/spaceturtle.yaml` | The agent's definition for `docker-agent`: its instruction, its file tool and the skills it loads. A release publishes it as it is |
| `images/agent/Dockerfile`, `images/connector/Dockerfile`, `images/connector/connector-start` | The agent's zone image (`docker-agent`'s sandbox image plus `toon`, no wallet or key, and `docker-agent` built again with the banner, see below) and the connector's zone image (`toon`, the container engine, gVisor's `runsc`), and `connector-start`, which starts the engine, the two forwarders an agent key is used through and the supervisor without `systemd --user` |
| `images/agent/docker-agent.patch`, `images/agent/banner.awk`, `images/agent/spaceturtle-apps`, `images/agent/spaceturtle-limit` | The two changes to `docker-agent` the agent's zone carries, `--banner-file` and `--sidebar-section` (ADR 0005), what lists the node's apps and shows the agent key's spending limit for the sidebar, and what makes the film of frames it plays: the turtle of `docs/assets/spaceturtle-banner-dark.svg` in a field of stars 240 characters wide and 64 high, of which the chat shows the middle. The image build is given `docs/assets` as the build context named `assets` |
| `images/versions.env`, `images/versions` | Every pin the two images add, with its checksum, and the `docker-agent` program a release publishes with; the command that prints the images' versions for release notes |
| `.github/workflows/images.yml` | Builds both images on every change to `images/`. It does not publish |
| `release/references`, `release/publish-definition`, `release/mark-latest`, `release/notes` | What a release publishes, under which names; the definition pushed to each registry and read back, byte for byte; `latest` moved to a release once it is all published; the release's notes |
| `.github/workflows/release.yml` | A tag `vX.Y.Z` runs the gate, then publishes the definition and both images. See [Releasing](releasing.md) |
| `tests/check-images` | Checks that no Dockerfile carries a version of its own, that `toon` and gVisor are pinned and verified, that the agent's image names no passphrase, wallet or key, and that `images/versions` prints each pin |
| `tests/check-agent` | Checks an agent definition against the rules that keep the agent away from the money and from approving its own apps (ADR 0003), and that `docker-agent` will publish it as written |
| `tests/run` | The tests of the `being-observed` skill's answers, the launcher, `tests/check-agent`, `tests/check-images` and the `release/` scripts (against a stub `docker-agent`) |
